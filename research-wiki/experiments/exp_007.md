## ⚠️ 更正声明 (2026-04-11)

**本实验的核心前提有误。** R023/R024 测量的是 LFQ 离散 token 空间（通过 `vae.encode()` 获取），但 mT5 实际调用的是 `vae.encode_continuous()`（量化前连续隐变量），完全不经过 LFQ codebook。

- **R023 测量内容**：离散 token 的 codebook 利用率/熵 → 对 mT5 失败分析无关
- **R024 测量内容**：基于 LFQ token histogram 的 oracle 检索 BLEU4 → 不是 mT5 输入空间的上界
- **错误结论**（已撤回）：
  - ~~"LFQ tokenizer 是 mT5 翻译失败的瓶颈"~~
  - ~~"进入 G2-a：移除量化，用连续嵌入"~~ → mT5 已经在用连续嵌入
- **正确参考**：docs/research_history_zh.md 第 8.5 节已证明连续 VAE 嵌入有区分能力（62% 1024-way 分类准确率），问题在于 MLP projection + mT5 微调的训练过程，而非嵌入质量

## Motivation（历史记录，前提有误）

After R022 failed (F3 gate: ST-GCN VAE + direct mT5 → csl_BLEU4=0.993, gate ≥5.0, WORSE than baseline Conv1d 1.742), the primary failure hypothesis is **G8**: LFQ tokens trained with reconstruction objective are "acoustic class" not "semantic class". Neither Conv1d nor ST-GCN encoder produces tokens that support language modeling.

Two diagnostics are needed before committing to the next intervention:
1. **G1-a** (R023): Is the codebook actually being used? How much information entropy do the token sequences carry?
2. **G1-c** (R024): What is the theoretical upper bound of BLEU4 achievable with these tokens? (Oracle nearest-neighbor decoder)

## Experimental Design

### R023 — Codebook Utilization (G1-a)

**Script**: `scripts/analysis/g1_codebook_utilization.py`
**Method**: Encode 500 CSL-Daily train samples through both Conv1d VAE and ST-GCN VAE; compute per-part (body/lhand/rhand) statistics:
- Unique codes used / codebook_size (utilization rate)
- Shannon entropy of token distribution (bits)
- Dead codes (never-activated)
- Top-k concentration (fraction of total tokens in top-10/50/100 codes)

**Decision relevance**: If ST-GCN has much lower entropy/utilization than Conv1d, this explains why mT5 translation is worse despite better reconstruction — the ST-GCN codebook has collapsed to fewer effective codes, reducing the information available to the LM.

### R024 — Oracle NN Decoder (G1-c)

**Script**: `scripts/analysis/g1_oracle_decoder.py`
**Method**: For each val sample, find nearest neighbor in 2000 train samples by L1 distance on normalized token histograms; use the train sample's ground-truth text as prediction. Compute BLEU4 over 500 val samples.

**Interpretation thresholds**:
- oracle BLEU4 < 5 → tokenizer itself is the bottleneck (tokens don't discriminate between different signs/sentences)
- oracle BLEU4 ≥ 10 → tokenizer is fine; LM training is the bottleneck
- oracle BLEU4 5–10 → borderline; both contribute

**Why this matters**: If even a perfect retrieval oracle can't achieve BLEU4 > 5 using these tokens, then no amount of LM improvement will help — we need a fundamentally different tokenizer.

## Expected Outcomes

**If codebook is collapsed** (util < 20%, entropy < 30% of max):
→ ST-GCN encoder maps too many different poses to the same code
→ Fix: either use codebook diversity regularization, or abandon LFQ quantization (→ G2-a: continuous embeddings)

**If oracle BLEU4 < 5 for both Conv1d and ST-GCN**:
→ The token space is not discriminative enough for retrieval-based translation
→ Decision: proceed to G2-a (continuous embeddings) or G2-b (gloss-supervised codebook)

**If oracle BLEU4 is much higher for Conv1d than ST-GCN**:
→ ST-GCN tokens are specifically worse for semantic discrimination despite better reconstruction
→ This is the key insight for understanding G7/G8

## Connections to Prior Work

- Inspired by **HuBERT** (Hsu et al. 2021): "acoustic units" from K-means are sufficient for ASR but not for speech understanding — need "semantic units" from teacher-forced objectives
- Related to **MAGVIT-v2** (Yu et al. 2023): Lookup-Free Quantization was designed for visual tokenization and may have different properties than needed for sign language
- **Uni-Sign** (Li et al. 2025): uses pose tokens directly extracted from video without LFQ quantization — avoids this problem entirely by using continuous features
